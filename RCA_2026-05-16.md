# Root Cause Analysis: v2.0 Production Bug Incident

**Date:** 2026-05-16  
**Incident:** 8 bugs discovered in production immediately after v2.0 deployment  
**Severity:** Critical (check-ins failing, degraded UX for all users)  
**Detection Time:** ~15 minutes post-deploy (user report)  
**Resolution Time:** ~1 hour (hotfix deployed)  
**Impact:** 2 users affected, check-ins blocked, command UX degraded

---

## The Paradox: 1043 Tests Passed, Production Broke

This is the central mystery. Our test suite reported **1043 passed, 0 failed**. Our pre-deploy check reported **12/12 passed**. Yet within minutes of deployment, users encountered critical failures.

**The answer:** Our tests validate *services* and *business logic* in isolation. The bugs were all in *integration glue* — the code connecting Telegram handlers to services. None of our 1043 tests exercise the actual `ConversationHandler` callback-to-`finish_checkin()` path, the handler group propagation behavior, or the `_get_command_handler_map()` consistency.

---

## Bug-by-Bug Root Cause Analysis

### Bug 1: UnboundLocalError — `DailyCheckIn` in `finish_checkin()`

**What happened:** A nested `from src.models.schemas import DailyCheckIn` inside a `try` block at line 1242 caused Python to treat `DailyCheckIn` as a local variable for the entire `finish_checkin()` function. When line 1065 tried to instantiate it (before reaching line 1242), Python raised `UnboundLocalError`.

**Why this went to prod:**
1. **No integration test covers `finish_checkin()` from callback context.** All tests that touch check-in completion either mock `finish_checkin` or test it in isolation with a mock `Update` object that has `.message` set.
2. **No static analysis for Python scoping anti-patterns.** `pylint` or `flake8` with scoping rules would flag nested imports inside functions that shadow module-level names.
3. **Code review missed the nested import.** The PR that added goal integration (line 1242) introduced this import without realizing it shadowed the module-level import at the top of the file.
4. **The bug only manifests in the callback path.** The Q5 mood handler calls `finish_checkin()` from a callback query context. Most local testing used the command path (`/checkin` without mood Q5, or quick check-in) which bypassed this code path.

**Process failure:** Code review → Testing → Local validation

---

### Bug 2: `update.message` is `None` in callback queries

**What happened:** `finish_checkin()` assumed `update.message` always exists and called `update.message.reply_text()` 12 times. But when triggered from an inline button callback (Q5 mood), `update.message` is `None` and only `update.callback_query.message` exists.

**Why this went to prod:**
1. **Developer didn't understand Telegram Update structure.** In `python-telegram-bot`, `Update` objects from callbacks have `.message = None`. This is PTB 101.
2. **No callback-query integration tests.** `test_conversation_flow.py` tests state transitions but mocks the update object with `.message` always present.
3. **Local testing used command path, not callback path.** Developers typed `/checkin` and entered text responses. They never tapped inline buttons for the mood Q5 flow because that requires the full 5-state conversation.
4. **No pattern enforcement for safe message access.** No linter rule or helper function required safe message retrieval.

**Process failure:** Framework knowledge → Testing coverage → Local validation

---

### Bug 3: "Did you mean" after successful commands

**What happened:** The `handle_unknown_command` handler registered in **group 2** fires after every command because PTB processes handlers in ALL groups sequentially, not just the first match.

**Why this went to prod:**
1. **Fundamental misunderstanding of PTB handler groups.** The developer believed group 2 would only fire if groups 0 and 1 didn't match. PTB actually runs ALL matching handlers across ALL groups.
2. **No integration test for command routing.** Tests verify individual command handlers but don't test the routing pipeline.
3. **No handler conflict detection.** There's no automated check that verifies "a command in REGISTERED_COMMANDS should not also trigger handle_unknown_command."
4. **Fuzzy matching was added late in development** (Phase 3E) and wasn't fully regression-tested against all existing commands.

**Process failure:** Framework knowledge → Architecture review → Regression testing

---

### Bug 4: Missing commands in `_get_command_handler_map()`

**What happened:** 15 new v2.0 commands were added to `REGISTERED_COMMANDS` and handler registrations, but `_get_command_handler_map()` (used for fuzzy matching and programmatic dispatch) wasn't updated.

**Why this went to prod:**
1. **Registry drift — three sources of truth.** Commands exist in: (a) `REGISTERED_COMMANDS` list, (b) `add_handler(CommandHandler(...))` calls, (c) `_get_command_handler_map()` dict. There is no automated verification that these stay in sync.
2. **No compile-time or test-time check for handler map completeness.** A simple test iterating `REGISTERED_COMMANDS` and asserting each exists in the handler map would have caught this.
3. **Feature additions were scattered across multiple PRs.** Each new command was added individually without a checklist requiring "update REGISTERED_COMMANDS, add handler registration, add to handler map."
4. **The bug is latent — it only manifests when fuzzy matching triggers.** Most commands worked fine because `CommandHandler` in group 0 matched them. The missing map only broke auto-execute/suggest paths which are edge cases.

**Process failure:** Code review checklist → Automated consistency checks → Single source of truth

---

### Bug 5: Constitution HTML parse error (`<6` treated as tag)

**What happened:** The hardcoded constitution text contained `2+ nights of <6 hours sleep`. When sent with `parse_mode='HTML'`, Telegram rejected it as an invalid HTML tag.

**Why this went to prod:**
1. **No HTML escaping for user-facing strings.** Any string with `parse_mode='HTML'` must be sanitized or use `html.escape()`.
2. **The constitution text was hardcoded and never rendered in tests.** `test_constitution_command.py` mocks the service response but doesn't actually send it through Telegram's parser.
3. **Local testing used `parse_mode=None` or didn't reach this line.** The developer likely tested with a fresh user who didn't have enough check-ins to trigger the historical patterns section.
4. **No lint rule for unescaped `<` in strings sent with `parse_mode='HTML'`.**

**Process failure:** Output sanitization → Testing with real parse modes → Static analysis

---

### Bug 6: Feedback NPS raw HTML tags

**What happened:** The NPS callback used `<b>Thank you!</b>` but didn't specify `parse_mode='HTML'`, so users saw raw tags.

**Why this went to prod:**
1. **Inconsistent `parse_mode` usage.** Some messages use it, some don't. No enforcement.
2. **Copy-paste from other handlers that DO use parse_mode.** The developer copied HTML formatting from a handler that had `parse_mode='HTML'` but forgot to include it.
3. **Visual testing impossible in automated tests.** Tests check function calls but can't verify Telegram rendering.
4. **No code review checklist item:** "If message contains HTML tags, verify `parse_mode='HTML'` is set."

**Process failure:** Code review consistency → Visual QA → Lint rules

---

### Bug 7: Deprecated Gemini model (`gemini-2.0-flash-exp`)

**What happened:** `query_agent.py` hardcoded an experimental model name that was removed from Vertex AI.

**Why this went to prod:**
1. **Model name is hardcoded in the file, not centralized in config.** Every agent has its own default model name scattered across files.
2. **No integration test for QueryAgent.** `test_query_agent.py` doesn't exist. The query agent is only triggered by general messages, which are mocked in tests.
3. **No model version validation at startup.** The app doesn't verify model availability on boot.
4. **Experimental model names aren't tracked.** There's no inventory of which models we depend on and their deprecation timelines.
5. **QueryAgent is a fallback path.** It's only used when the supervisor classifies a message as "query" intent, which is rare. Most messages go to emotional or checkin intents.

**Process failure:** Configuration management → Integration testing → Dependency tracking

---

### Bug 8: Supervisor attribute error (`user.last_checkin_date`)

**What happened:** `supervisor.py` referenced `user.last_checkin_date` and `user.mode` but the `User` schema stores these in `user.streaks.last_checkin_date` and `user.constitution_mode`.

**Why this went to prod:**
1. **Refactoring without updating all references.** The `User` schema was refactored to nest streak data in a `StreakData` sub-object, but not all code paths were updated.
2. **The supervisor is only used for general messages, not commands.** Most testing uses direct commands (`/checkin`, `/support`) which bypass the supervisor entirely.
3. **No mypy/static type checking.** With strict type checking, `user.last_checkin_date` would fail because `User` doesn't have that attribute.
4. **The error is a WARNING, not an exception.** The supervisor catches the error and falls back to `None`, so it doesn't crash — it just degrades silently. Silent degradation is worse than crashing because it hides the bug.

**Process failure:** Type safety → Refactoring hygiene → Error severity classification

## Systemic Process Gaps

### 1. No Staging Environment

**Gap:** Code goes directly from local dev → production. There is no staging Cloud Run service where we can test real Telegram webhooks, inline buttons, and callback queries.

**Impact:** Callback query bugs, handler group bugs, and rendering bugs only appear in production.

**Fix:** Create `accountability-agent-staging` Cloud Run service with a separate Telegram bot token (test bot). All deployments go to staging first for 24h before production.

---

### 2. Tests Test Services, Not Handlers

**Gap:** 1043 tests cover services, utilities, and agents. <10 tests cover the actual Telegram bot handlers (`telegram_bot.py`, `conversation.py`). The `ConversationHandler` state machine, callback routing, and handler group propagation are untested.

**Impact:** All 8 bugs were in handler/integration code, not service code.

**Fix:**
- Add integration tests that simulate full `/checkin` flow through all 5 states
- Add integration tests for callback queries (inline button taps)
- Add test for handler group propagation (verify `handle_unknown_command` doesn't fire after real commands)
- Add test for `_get_command_handler_map()` completeness

---

### 3. No Code Review Checklist for Handler Changes

**Gap:** New commands and handlers are added without a standardized checklist.

**Impact:** Missing handler map entries, missing parse_mode, inconsistent registration.

**Fix:** Create a `HANDLER_CHECKLIST.md`:
```markdown
## Adding a new command
- [ ] Add to `REGISTERED_COMMANDS`
- [ ] Add `CommandHandler` registration in `_register_handlers()`
- [ ] Add to `_get_command_handler_map()`
- [ ] Add to `COMMAND_KEYWORDS` if applicable
- [ ] If message uses HTML tags, set `parse_mode='HTML'`
- [ ] If callback query handler, use `_get_message_from_update()` for replies
- [ ] Add rate limiting tier in `_check_rate_limit()`
- [ ] Add test in `test_telegram_bot_commands.py`
```

---

### 4. No Static Analysis for PTB Patterns

**Gap:** No lint rules or static analysis for common python-telegram-bot anti-patterns.

**Impact:** `update.message` crashes, handler group issues, parse_mode inconsistencies.

**Fix:** Add custom lint rules or a pre-commit check:
- Flag `update.message.reply_text` inside callback handlers
- Flag strings with `<b>`, `<i>`, `<code>` sent without `parse_mode='HTML'`
- Flag `MessageHandler(filters.COMMAND)` in group >0 without guard against registered commands
- Flag nested imports inside functions that shadow module-level imports

---

### 5. Feature Flags Exist But Aren't Used

**Gap:** We added 16 feature flags in `config.py` but most features are always-on. The flags aren't wired to handler registration.

**Impact:** When bugs are found, we can't quickly disable features. We had to deploy a code hotfix instead of flipping a flag.

**Fix:** Wire feature flags to handler registration:
```python
if settings.enable_mood_tracking:
    self.application.add_handler(CallbackQueryHandler(
        self.mood_callback, pattern="^mood_"
    ))
```
Add a `/admin/feature_flags` endpoint to toggle flags without redeploying.

---

### 6. No HTML Sanitization Layer

**Gap:** Any string can be sent with `parse_mode='HTML'` without escaping.

**Impact:** Constitution parse error, potential XSS-style injection via user data.

**Fix:** Create a `safe_send_html()` wrapper:
```python
from html import escape

def safe_send_html(message, text, **kwargs):
    # Escape any raw < or > that aren't our intended tags
    safe_text = sanitize_telegram_html(text)
    return message.reply_text(safe_text, parse_mode='HTML', **kwargs)
```
Ban direct `reply_text(..., parse_mode='HTML')` in favor of the wrapper.

---

### 7. Configuration Drift — No Single Source of Truth

**Gap:** Model names, handler registrations, and command lists are scattered across files.

**Impact:** Query agent used deprecated model, handler map was incomplete.

**Fix:**
- Centralize model names in `config.py`
- Auto-generate `_get_command_handler_map()` from `REGISTERED_COMMANDS`
- Add a `verify_handlers.py` script that runs at test time to check consistency

---

### 8. No Manual QA Step

**Gap:** After tests pass and pre-deploy checks pass, code goes straight to production without a human doing a sanity check.

**Impact:** Visual bugs (raw HTML), UX flow bugs (did you mean), and callback flow bugs weren't caught.

**Fix:** Add a **Manual QA Gate** to the deployment process:
1. Deploy to staging
2. QA engineer (or developer) runs through:
   - `/start` → full onboarding
   - `/checkin` → all 5 questions including mood Q5
   - `/quickcheckin`
   - `/constitution`
   - `/feedback`
   - Each new command
3. Sign-off required before production deploy

---

### 9. No On-Call Runbook for Rollback

**Gap:** When bugs were reported, we had to diagnose, fix, rebuild, and redeploy. There was no instant rollback option.

**Impact:** ~1 hour of broken production.

**Fix:**
- Keep last 3 production image tags documented
- Create a one-command rollback script:
  ```bash
  ./scripts/rollback.sh accountability-agent-00011-qd8
  ```
- Add circuit breaker: if error rate >5% for 2 minutes, auto-rollback to previous revision

---

### 10. Pre-Deploy Check Is Too Shallow

**Gap:** `scripts/pre_deploy_check.py` only checks: compilation, tests, imports. It doesn't check:
- Handler registration consistency
- HTML sanitization
- Feature flag wiring
- Model name validity
- Callback handler safety

**Impact:** All 8 bugs passed the pre-deploy check.

**Fix:** Expand pre-deploy check:
```python
# New checks to add
check_handler_map_completeness()  # All REGISTERED_COMMANDS in handler map
check_html_safety()               # No unescaped < in HTML parse_mode strings
check_model_names()               # All model names are valid and accessible
check_feature_flag_wiring()       # All flags referenced in config are used
check_callback_safety()           # No update.message in callback handlers
```

## Summary: The Five Whys

**Why did check-ins fail in production?**
→ `finish_checkin()` crashed with `UnboundLocalError`.

**Why did `finish_checkin()` crash?**
→ A nested import shadowed the module-level import, making `DailyCheckIn` a local variable.

**Why wasn't this caught by tests?**
→ No test exercises `finish_checkin()` from a callback query context (Q5 mood path).

**Why wasn't this caught by code review?**
→ No checklist or lint rule flags nested imports that shadow module-level names.

**Why did this reach production?**
→ **We have no staging environment, shallow pre-deploy checks, no handler integration tests, and no code review checklist for handler changes.**
